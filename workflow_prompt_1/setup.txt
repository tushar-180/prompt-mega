SETUP WORKFLOW, BDE DIGITAL PROSPECTING SYSTEM

I am setting up a pre-sales prospecting workflow for our software development and IT services business.

The purpose of this run is to build the exact workspace structure, folders, lists, sheets, tabs, task records, and rules that the later "Digital Prospect Audit & Outreach" master workflow depends on. Everything the master workflow reads or writes has to exist and be named exactly as written here, otherwise that run will fail partway through.

This is a SETUP RUN ONLY.

Do not research prospects.
Do not create outreach.
Do not send emails.
Do not invent existing company data.

All dates in this system use the Asia/Kolkata time zone. Any date field you create, any date you record, and any date rule you write is read in that time zone (time zone: Asia/Kolkata).


SCENARIO DATES AND CLICKUP CREATION TIMESTAMPS, READ THIS BEFORE SEEDING

The master workflow runs against a fixed scenario date, 2026-08-31 in Asia/Kolkata for the first cycle. That date decides what the master run writes into Last Audit Date and Review Cycle. It is not a claim about when this data was created, and it is not a filter on the queue.

ClickUp stamps its own creation timestamp on every task at the moment it is created, and that timestamp cannot be backdated through the API or the interface. The seven seeded tasks will therefore carry the real wall clock date of this setup run, which will normally fall after 2026-08-31. That is expected and correct. Do not try to backdate a creation timestamp, do not fake one in a record key, and do not hold off on seeding because the dates look inconsistent with the scenario date.

Because of that, a ClickUp creation timestamp is never an eligibility test. A task is eligible on the scenario date regardless of when ClickUp says it was created. The creation timestamp has exactly one job in this system, the second tie breaker in queue order, and it is read at full precision from the ClickUp API rather than from the minute shown on screen, because all seven seeds are created inside the same minute.

Write both of those rules onto the Prospecting Rules tab exactly as set out in the Google Sheet section below. The master workflow treats that sheet as authoritative wherever the sheet and its own brief disagree, so the sheet is where this gets settled. A master run that reports zero eligible prospects because every task was created after the scenario date has misread the queue, and these rows are what stop that happening.

WHAT THE CLICKUP FREE PLAN ALLOWS, AND WHAT THIS SYSTEM THEREFORE USES

This system is built to run entirely on ClickUp Free Forever. Everything below is inside that plan.

Custom fields are the trap. Free Forever does not block them outright, it grants a fixed 100 uses of the feature, and that allowance never resets. Once it is spent, creating another field fails and, worse, saving a value into a field that already exists fails too, with the message that Custom Fields is not available on your current plan. An earlier version of this setup burned that allowance building a 30 field schema and left the workspace unable to write to any of them. There is no way back from that short of paying.

So this system uses no custom field at all. Create none, and treat any that already exist as inert: leave them exactly where they are, write nothing into them, and say in the setup report that they exist and are unused. Deleting them is not this run's job and would not refund the allowance anyway.

Everything lives instead in the two places the Free plan gives you without a meter: the task description and task comments.

Four other Free plan limits shape this setup:

Five Spaces per workspace. If the workspace already holds five Spaces and none of them is Sales, do not try to create a sixth. Put the Folder in whichever existing Space the team uses for sales work, record the Space you used in the setup report, and note it as a deviation, since the master brief names Sales and will need telling. Forty Lists per Space and a hundred Folders per Space are the other structural caps, and this system needs one of each, so neither will bite.

A hundred API requests per minute. A run that reads and rewrites task descriptions in a loop can reach that, and the symptom is a request failing rather than a clear message. Work steadily, one task at a time, and if a call fails on rate limiting, wait and repeat it rather than treating it as a blocked step.

Plain comments are free and unlimited, which is what this system posts. Assigned comments, meaning a comment assigned to a person as an action item, are not on the Free plan. Never assign a comment, on any task, at any point.

Automations are capped at five rules and a hundred executions. This system uses none, so build none.

Company Name is the ClickUp task name. There is no Company Name key, because a company's name has one home and that is the title of its task.

Twenty six keys, and the rules that govern them:

All twenty six are present on every task, in that order, always, including the ones holding nothing. A key with nothing after its colon is empty, and empty is a normal state that the master workflow reads and writes. A key that is absent altogether is a broken record, and the master workflow treats that task as Needs Review and names the missing key rather than guessing at it. This is the one thing that replaces the old field manager check, so get it right at seed time.

Five keys hold lists rather than a single value: Website Findings, Search Visibility Findings, PageSpeed Findings, Evidence / Sources and Competitors Reviewed. Their key line stops at the colon, and each item sits on its own line underneath, opening with a hyphen and a space. The item belongs to the nearest key line above it. Every other key holds a single line of text after its colon.

The two marker lines are written character for character as shown, including the square brackets. Anything in the description above the opening marker or below the closing marker belongs to whoever typed it, and is preserved exactly.

To change a record, read the whole description first, alter only the key lines you were told to alter, and write the description back with every other character identical. Never rebuild a record from memory, and never write a description that drops a key you did not have a value for. Rebuilding from memory is how BDE Notes gets lost.

BDE Notes sits inside the block like any other key, and the master workflow reads it and never rewrites it. Prospect Source is the same.

The allowed values for each key live on the Record Schema tab of the Google Sheet, described below. That tab is what a ClickUp dropdown used to be: the list of values the master workflow is permitted to write. Nothing in ClickUp enforces it now, so the tab is what stands between the system and a made up status, which is why it gets built before any task is seeded and why this setup run is not complete until it exists and can be read back off the screen. The master brief carries a fallback copy of these values so a master run never stops over a missing tab, but that fallback is a safety net for that run and not a substitute for building the tab here, and a sheet finished with six tabs is a failed setup.

Plain text only inside the block. No bold, no headings, no tables, no links wrapped in markup. ClickUp will render the item lines as bullets and that is fine, since the text and its order survive; anything fancier does not.


BUILDING THE RECORD ON A TASK

The ClickUp MCP integration can write a task description, which means the audit record needs no browser work and none of the field manager trouble the earlier version of this setup ran into. Write the block as part of creating the task, or as an update to a task that already exists.

On a task that already exists and has no block, add one, filling the keys from whatever that task already holds and leaving the rest empty. On a task that already has a block, leave it alone unless a value is wrong.

After writing any description, read the task back and confirm the block came through with all twenty six keys and both markers. A description write that silently truncated or reformatted is the failure mode here, and reading it back is the only way to see it.
