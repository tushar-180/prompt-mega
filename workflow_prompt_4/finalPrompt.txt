The pull request number on the record is a claim in the same way the repository is, so what settles which pull request to work is the branch named on that record, and the open pull request whose head is that branch, in the repository that survived the check above, is the 1 to read whatever number GitHub has put on it. A number quoted on the record that opens nothing is somebody quoting a number off another tracker rather than evidence gone missing, so it does not hold the incident up and it does not get hunted for in another repository, and the number the branch really carries gets recorded as a correction. A branch with no open pull request behind it at all is a different thing, that is evidence that is not there, and the incident holds on it. Off that pull request take the changed files, any migration file, any rollback script and the test evidence. Whether the tests passed is settled by the most recent completed GitHub Actions run on the head commit of that pull request and by nothing else, so where a Jira comment says testing is complete and that run shows a required job failed, was cancelled or never ran, the testing is incomplete and the incident cannot be a release candidate on that evidence. Where the pull request carries a migration, read it, work out whether it moves the schema or the data, and a rollback that would put the older schema back and drop rows written after the migration went out is not a rollback at all, it is a second incident waiting to happen. Where the pull request carries no migration, the rollback script sitting in it is the evidence on its own and nothing further hangs on how thin or how thorough it reads, so what is written inside a rollback script only settles anything where there is a migration for it to undo.

An incident only earns an emergency window where the severity on the record reads Sev1 or Sev2 or the approved root cause names a confirmed security exposure, and on top of that a rollback script sits in the pull request and the completed Actions run shows every job passing. A rollback script sitting in that pull request meets the 2nd half of that whatever the script reads, unless there is a migration for it to undo, so a route that clears both halves does not get held back on a doubt with nothing behind it.

Every incident ends the run carrying exactly 1 of these 4 recovery readiness statuses, never 2 and never none, and where more than 1 fits the one higher up this list wins. No Release Required is where recovery rests on the client or a third party and nothing has to ship from here. Hold Unsafe Or Incomplete Evidence is where a required job failed or never ran, or no rollback script sits in the pull request at all, or the pull request carries a migration whose rollback would lose data, or the evidence could not be read at all even after Chrome below had been tried. Emergency Release Candidate is where the route is clean and the emergency test above is met. Scheduled Release Candidate is everything else with a clean route that can wait, including a candidate that lost a window on capacity rather than on anything technical.

Only an Emergency Release Candidate competes for a window. The order runs off this chain, read left to right and stopping at whichever test separates 2 incidents: a Sev1 on the record, which separates a Sev1 from everything under it and never a Sev2 from a Sev3, a confirmed security exposure, the larger affected user count, the earlier incident start timestamp, and a tie still standing goes to the alphabetically smaller Incident ID. No more than 2 windows get allocated in 1 run whatever the sheet shows going spare, so where more candidates qualify than that, the ones highest on the chain take the 2 and the rest drop to Scheduled Release Candidate with the reason recorded as capacity rather than a technical fault. The 2 windows used are the 2 earliest going spare on Window Date, so any free window past those comes back unused and gets counted that way. Which of those 2 each incident takes runs off that same chain, the higher one taking the earlier window, unless the lower one has a workaround expiring first, in which case it goes earlier so it is covered before the workaround runs out.
