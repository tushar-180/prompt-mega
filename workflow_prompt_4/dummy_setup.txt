WHAT GOES INSIDE THE 3 CLEAN ROLLBACK SCRIPTS

inc-2041-rollback.sh, inc-2042-rollback.sh and inc-2045-rollback.sh are evidence in their own right, not filler, because the master run opens them to work out whether a route is safe to ship. A script that only echoes a line and exits reads on the screen as a rollback that does not roll anything back, and a master run that opens 1 of those is right to refuse the route on it, which quietly kills 3 of the 5 code incidents this seed exists to set up. So write all 3 out properly.

Each of the 3 is a short shell script that plainly does the work. It reads the release tag currently carrying the Latest badge in its own repository into a variable rather than having a version number typed into it, redeploys that release, restarts the named service, then runs a health check in a short retry loop and exits non zero if the service does not come back healthy. Put set -euo pipefail at the top and a header comment saying in plain words that it returns the service to the last known good release and touches no data and no schema. Roughly 25 lines is about right.

None of the deployment tooling these scripts call has to exist anywhere, and none of the 3 is ever going to be executed by anybody. They sit in a pull request as evidence for a person reading them, so what matters is that the logic on the screen is real and complete, not that every command resolves to a real binary on a real host. Do not stop and ask me what the deployment commands are. Use exactly the ones below so all 3 scripts read the same way.

Read the tag with gh release view --json tagName --jq .tagName, run from inside the repository, which picks up the Latest badge and steps over a pre release on its own, and exit non zero with a message if it comes back empty. Redeploy with blackpine-deploy release --service NAME --tag TAG and restart with blackpine-deploy restart --service NAME. Health check with curl -fsS --max-time 10 against https://NAME.blackpine.internal/healthz, up to 5 attempts 10 seconds apart, exiting 0 on the first healthy response and non zero after the last one fails. NAME is payments for inc-2041 in blackpine-payments-api, billing for inc-2042 in blackpine-billing-api and checkout for inc-2045 in blackpine-web-portal, and it reads the same in all 3 places it appears in a given script.

Do not type a release tag into any of the 3. v4.2.0 in particular must not appear anywhere inside inc-2041-rollback.sh, because a rollback pointing at a tag that is not the one in production is a trap this seed is not trying to set and it will hold INC-2041 on its own. Do not write TODO or placeholder into any of them, do not leave any of the 3 as an echo and exit stub, and do not make any of them touch a database, a table or a schema.

The 1 rollback that is meant to look wrong is the ledger one on blackpine-payments-legacy, and that is a migration rollback rather than 1 of these 3.

Incident INC-2046 needs no code change at all, so it gets no repository, no branch and no pull request. That is deliberate, and the master run is supposed to read the root cause and land on No Release Required rather than holding it for missing evidence.

Leave all 5 pull requests open. Do not merge, approve or request changes on any of them, and do not open a single issue in any of these repositories.
