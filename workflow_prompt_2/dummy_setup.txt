SETUP WORKFLOW, TENDER BID DECISION SYSTEM

I am setting up a pre bid tender evaluation workflow for our software development and IT services business.

The purpose of this run is to build the exact workspace structure, folders, sheets, tabs, documents, Notion databases, Jira projects, components, issues and calendar that the later Tender Bid Decision master workflow depends on, and to fill it with sample tender data that workflow can be tested against. Everything the master workflow reads or writes has to exist and be named exactly as written here, otherwise that run will fail partway through.

This is a SETUP RUN ONLY.

Do not evaluate the tender.
Do not decide Bid, Conditional Bid or No Bid.
Do not create the compliance issues, the decision page, the calendar events or the email draft that the master run creates.
Do not send any email.
Do not put real client, employee or company confidential data anywhere in this seed.

All dates in this system use the Asia/Kolkata time zone. Any date field you create and any date you write is read in that time zone.


THE DATA YOU ARE SEEDING IS FICTIONAL, AND IT HAS TO LOOK IT

The buyer ABC Government Health Department, the tender ABC-HMS-2026-001, every person named below and every project named below are invented for testing. None of them is a real organisation, a real public tender or a real member of staff. Every document you create in Google Drive opens with this line on page 1, before anything else:

SAMPLE TEST DOCUMENT, NOT A REAL TENDER, CREATED FOR WORKFLOW TESTING ON 2026-09-01.

Keep that line in. It costs the master run nothing and it stops a seeded file being mistaken later for a real tender document. Do not put a real government department name, a real company letterhead, a real officer name or a real digital signature on any seeded document, and do not copy a real published RFP wholesale into one.


WHERE WEB SEARCH COMES IN, AND WHERE IT DOES NOT

Two things come off the live web and nothing else does.

One, the Portal URL cell. Search for a public tender notice or tender listing page on a real government e procurement portal that opens fully in Chrome without a login and without a captcha wall, open it to confirm that, and write that exact URL into the Portal URL cell of the target row. That page carries no notices for a fictional reference, and that is expected and fine. It is there so the master run's portal step reaches a page that genuinely opens rather than a dead address, and so the blocked portal branch is not the only branch the test ever exercises. Say in the report which URL you used and that you confirmed it opens with no account.

Two, the wording of the seeded clauses. Read a couple of real published government IT tender documents to see how eligibility, technical and SLA clauses are normally phrased, and write the filler clauses in that register. Take the style, not the text. Do not lift more than a sentence from any one source, and do not carry across a real buyer name, a real tender reference or a real bidder name.

Everything else in this seed is the hard text written out below. Where a clause is given in quotation marks below, write it exactly as given, because the master run's decisions turn on those words. Where the instruction says write your own, write ordinary plausible content that a hospital management system tender would carry.


BEFORE YOU START, CONNECTIONS AND TOOLS

Confirm you can reach Google Drive, Google Sheets, Google Calendar, Gmail, Notion and Jira, and confirm the Chrome browser plugin is available. Nothing here is called missing, unauthorized or blocked until the Chrome browser plugin has been pointed at it and failed too, so where one of those is not connected, errors, times out, refuses the call, reports a tool it does not recognise, returns nothing where the screen shows something, or hands back something that does not match what the screen shows, do that piece through Chrome instead, carry on with the setup, and say in the report which route you used and what error sent you there. Stop and name the piece only where Chrome cannot reach it either, quoting the error from both attempts. Do not report the setup as complete when a required piece could not be built by either route.

A report that says an app is not connected, not authorised or not working is not a finished setup run. The browser is the second route and it is expected to be used, not treated as a last resort, so an integration that fails is a reason to open the app in Chrome and carry on rather than a reason to stop. Retry once where a failure looks transient and wait out a rate limit rather than falling back for it. Where the integration and the screen disagree about what is there, the screen is what the workspace actually holds.

In practice, through Chrome, that means creating or renaming a Google Sheet tab where the Sheets connection cannot, typing the seed rows into the sheet on screen, creating the Drive folders and opening each seeded document to confirm the page markers and page breaks survived the save, creating the Notion teamspaces, databases and properties and adding records where the Notion connection cannot add a property or a select option, creating the Jira projects, choosing the project key, adding the components under project settings, creating and assigning issues and setting Due dates, creating the Bid Management calendar under calendar settings, and confirming the Gmail address and that Drafts holds nothing with the [ABC-HMS-2026-001] prefix. Never use Chrome to send an email during this run.

Note the Gmail address of the single signed in account before you start. It goes into the Bid Owner Email cell of the target row, so the draft the master run leaves unsent is addressed back to the person running the test and nothing can leave the workspace even if something goes wrong.
