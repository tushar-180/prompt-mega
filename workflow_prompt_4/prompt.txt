Title : Emergency Recovery Route Readiness and Limited Release Slot Allocation

Prompt : 
Open **Jira** and open the Jira site **Acme Engineering Jira**. Open the Jira project **Incident Recovery Management** and then open the **Incident Recovery Record** issue type. From the **Incident Recovery Management** project, review the incidents currently marked as pending recovery review. Process only the seven incidents that are in scope for this recovery review. Do not scan or process unrelated incidents.

For each incident, open its **Incident Recovery Record** in the **Incident Recovery Management** Jira project. Read the Incident ID, Client ID, affected service, approved technical root-cause record, confirmed commercial route, incident severity, incident start timestamp and current workaround information. Treat the approved root-cause record and confirmed commercial route as completed inputs. Do not change the root cause, do not decide whether the issue is a defect or change request, do not reinterpret contractual liability, do not change the commercial route and do not approve any commercial charge.

Open **PagerDuty** and open the **Active Incidents** view under the **Production Applications** service. Locate the matching incident using the Incident ID, affected service or Jira reference. Confirm the current incident severity, active status, affected service and affected-user information when available. Use PagerDuty only as supporting evidence for current incident impact and severity. Do not acknowledge, resolve, escalate or otherwise modify the PagerDuty incident.

Open **GitHub** and open the **acme-engineering** organization. For each incident, identify the exact production repository associated with the affected service. Use the repository information in the Jira **Incident Recovery Record** as the starting point, then verify the repository using the Client ID, repository path, relevant service directory, source-code module or symbol and production release tag. If two repositories contain similarly named modules such as `PaymentRecovery`, do not choose based only on the module name. Match the repository using the client, path, symbol and production release information.

Inside the correct GitHub repository, open **Releases** and **Tags** and identify the exact release tag currently deployed to production. Then open the proposed recovery branch and the related **Pull Request**. Never assume that the current `main` branch represents the production release. If the proposed fix exists on `main` but production is running an older release tag, evaluate the fix against the actual production release and verify compatibility before considering the recovery technically ready.

Inside the relevant GitHub **Pull Request**, inspect the changed files, database migrations, rollback scripts, dependency changes, feature-flag changes and test evidence. Check whether the proposed recovery method is compatible with the actual production release. Do not merge the pull request and do not change its approval state.

Open the relevant **GitHub Actions** workflow run linked to the recovery pull request and verify the actual automated test results. Do not rely only on Jira comments that say testing is complete. If Jira says testing is complete but the linked GitHub Actions test run shows that required test cases failed, treat the automated testing as incomplete.

Check all database migration files associated with the proposed recovery. Determine whether the recovery introduces a schema or data migration and whether a tested rollback script is available. If rollback would restore an older database or application state and could remove records created after the migration, do not recommend that rollback as a normal emergency recovery method. If the recovery is technically possible only by accepting material data-loss risk, classify the incident as **Leadership Risk Acceptance Required**.

Check all relevant feature-flag evidence in the production configuration and GitHub repository. Do not rely only on the status recorded in Notion. If the Notion record says that a feature flag is unused but the production configuration shows that the feature flag is enabled, treat the feature flag as active and correct the Notion record during the workflow.

Open **Confluence** only when a production runbook is referenced by the Jira **Incident Recovery Record**, GitHub recovery work or another authoritative recovery record. Open the **Engineering Operations** Confluence space and use the page **Production Emergency Release Runbook** as the applicable production runbook. Check its emergency release requirements, change-freeze rules, emergency exception rules, approval requirements, rollback requirements and production verification requirements. If a change-freeze exception exists in **Production Emergency Release Runbook**, apply the exception only when every condition defined by the runbook is satisfied.

Open **Google Drive** and open the folder **Emergency Release Management**. Inside that folder, open the Google Sheet **Emergency Release Capacity Tracker**. Use the **Emergency Release Capacity Tracker** as the authoritative capacity record for the current emergency release period. Check the available emergency release windows, each window's duration, existing allocations, blackout periods and internal release restrictions. Do not create another capacity entry when the same release period already exists in the sheet.

Open **Google Calendar** and open the calendar **Engineering Emergency Releases**. Search this calendar for available internal emergency release windows for the current release period. For this evaluation, only 120-minute emergency release windows may be allocated. Do not allocate a window that conflicts with an existing internal event, blackout period or release restriction. Do not invite any client attendee. If an incident already has an internal Calendar event, update that existing event instead of creating a duplicate event.

Evaluate the available recovery methods for every incident. Consider rollback, configuration change, feature disablement, isolated hotfix and scheduled permanent remediation when those options are technically applicable. Reject any recovery option when available evidence shows that it could cause data loss, restore an older security vulnerability, break another active client customization, depend on an untested migration, depend on an unavailable dependency or require access that is not available.

If a temporary workaround is safe and stable but the permanent fix does not have sufficient rollback evidence, classify the incident as **Workaround Only**. If all available recovery methods carry an identified unacceptable technical risk, classify the incident as **Hold, Unsafe Recovery Route**. If recovery may be technically possible but requires acceptance of a material data, security or multi-client impact risk, classify the incident as **Leadership Risk Acceptance Required**. If required test, rollback, migration, dependency or production-version evidence is missing, classify the incident as **Hold, Missing Technical Evidence**. If recovery depends entirely on client action or third-party action and no internal deployment is required, classify the incident as **No Technical Release Required**.

Every in-scope incident must receive exactly one of these seven statuses: **Emergency Release Candidate**, **Scheduled Release Candidate**, **Workaround Only**, **Hold, Missing Technical Evidence**, **Hold, Unsafe Recovery Route**, **Leadership Risk Acceptance Required** or **No Technical Release Required**.

Only incidents classified as **Emergency Release Candidate** may compete for the limited emergency release capacity. For this evaluation, seven fictional incidents compete for two 120-minute emergency release windows. When more than two incidents qualify, rank them in this exact order: active full-service outage, confirmed risk of permanent data loss, confirmed security exposure, larger number of currently affected users, sooner workaround expiry, earlier incident start timestamp and finally alphabetically smaller Incident ID. Never prioritize an incident because the client has greater commercial value.

Use the **Emergency Release Capacity Tracker** Google Sheet and the **Engineering Emergency Releases** Google Calendar to reconcile emergency capacity. Allocate no more than two emergency release windows. Every selected incident must receive one matching internal Calendar hold. Report the total available windows, allocated windows and unused windows. These numbers must reconcile exactly.

Open **Notion** and open the **Acme Engineering** workspace. Open the database **Emergency Recovery Readiness Register**. Use **Incident ID + Target Recovery Version** as the unique record key. Search the **Emergency Recovery Readiness Register** for an existing record using that exact combination before creating anything. If the record already exists, update it. Do not create a duplicate record.

Every record in the **Emergency Recovery Readiness Register** must contain Incident ID, Client ID, Affected Service, Confirmed Root-Cause Record, Confirmed Commercial Route, Production Repository, Production Release Tag, Proposed Recovery Method, Fix Branch or Pull Request, Database Migration Impact, Rollback Availability, Rollback Risk, Feature-Flag Option, Dependency Impact, Automated Test Result, Manual Verification Required, Open Jira Blockers, Runbook Status, Recovery-Readiness Status, Priority Score, Allocated Calendar Slot, Hold Reason, GitHub Issue, Leadership Review Requirement and Last Reviewed Timestamp.

Return to the matching Jira **Incident Recovery Record** in the **Incident Recovery Management** project and update the recovery-readiness information after completing the technical evaluation. Record the final recovery status, proposed recovery method, actual production release tag, technical evidence, open blockers, Calendar allocation, hold reason, GitHub issue and leadership-review requirement. Do not change the approved root-cause record or confirmed commercial route.

When required technical evidence or technical work is missing, open the **acme-engineering** GitHub organization and search the relevant repository's **Issues** using the Incident ID and missing evidence description. If an existing issue matches the missing evidence, update that existing issue. If no matching issue exists, create one containing the Incident ID, affected service, missing evidence or technical work, production release version, completion condition and relevant Jira or pull-request reference. Do not create a GitHub issue when there is no missing technical evidence or technical work.

After completing the Jira, GitHub, Notion, Google Sheet and Calendar updates, open **Gmail** using the connected company Gmail account. Create exactly one unsent draft with the subject **Emergency Recovery Route Readiness and Release Slot Review**. Address the draft to the PM and technical leadership recipients already defined by the connected company account or existing workflow context. Do not invent new recipient addresses. The draft must summarize all seven incidents, their final recovery-readiness statuses, the two allocated emergency release windows, held incidents, hold reasons, GitHub evidence issues and incidents requiring leadership risk acceptance. Include the total available emergency windows, allocated emergency windows and unused emergency windows. Do not send the draft.

Do not merge any GitHub pull request. Do not deploy any code. Do not approve a production release. Do not change the approved root cause. Do not change the confirmed commercial route. Do not approve a commercial charge. Do not send the Gmail draft. Do not invite any client attendee to Google Calendar. Calendar events must remain internal engineering or leadership holds.

If any required application, page, record or document cannot be accessed through its native integration, use the **Chrome plugin** as the fallback. In Chrome, open the exact application and exact resource name defined in this workflow. For example, if the native Google Sheets integration cannot access **Emergency Release Capacity Tracker**, open Google Drive in Chrome, open the **Emergency Release Management** folder and then open **Emergency Release Capacity Tracker**. If Jira cannot be accessed natively, open **Acme Engineering Jira** in Chrome, open **Incident Recovery Management** and then open the relevant **Incident Recovery Record**. Use the same exact names and search criteria. Never silently skip a required source. If the required evidence still cannot be verified after using the Chrome fallback, classify the affected incident as **Hold, Missing Technical Evidence** rather than guessing.

Before finishing, perform a final reconciliation across **Acme Engineering Jira**, **Incident Recovery Management**, **PagerDuty Active Incidents**, the relevant **acme-engineering** GitHub repositories, the **Acme Engineering** Notion workspace, **Emergency Recovery Readiness Register**, **Emergency Release Management**, **Emergency Release Capacity Tracker**, **Engineering Emergency Releases** Google Calendar and Gmail. Confirm that every one of the seven in-scope incidents has exactly one recovery-readiness status, no more than two incidents have emergency release slots, every selected incident has one matching Jira recovery record, one matching Notion record and one matching Calendar hold, every missing-evidence case has an existing or newly created GitHub issue, existing records and Calendar events were updated without duplication, exactly one unsent Gmail review draft exists and the number of available, allocated and unused emergency release windows reconciles exactly.

The workflow ends after the single Gmail draft has been prepared and all records have been reconciled. Do not perform any deployment, merge, client communication or commercial approval after the final reconciliation.
