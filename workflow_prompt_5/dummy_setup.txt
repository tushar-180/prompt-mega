SETUP WORKFLOW, PRE CALL PRODUCT CLAIM CHECK SYSTEM

I am building the workspace that my master workflow, the pre call product claim check, reads and writes. Everything that master run opens has to exist first and be named exactly as written here, otherwise the run stops partway through.

This is deliberately small. 3 apps only, Salesforce, Notion and Slack. 7 account records, 10 sales call records of which 6 are in scope and 4 are decoys that must stay out of scope, 1 Salesforce report, 3 Notion databases holding 8 preparation records, 7 changelog entries and 7 feature rows between them, and 1 empty Slack channel. Do not pad it out, do not add records to make it look fuller, and do not invent items that are not listed below. Every single item here is carrying something specific, so build exactly what is written and nothing more.

The slow part is the Salesforce schema in Part 1. Everything after it is typing rows into things that already exist, so get Part 1 right and the rest goes quickly.

This is a SETUP RUN ONLY.

Do not verify any product claim.
Do not classify any claim as Current, Renamed, Replaced, Deprecated, Beta Only, Plan Restricted or Needs Product Confirmation.
Do not fill Verification Status, Verified Against Changelog Version, Verified On, Correction Summary or Last Alert Version on any preparation record. Those 5 properties exist and stay empty.
Do not correct, tidy, reword or improve any line of Preparation Notes. The notes are wrong on purpose.
Do not post any message in Slack, and do not create any channel other than the 1 named in Part 9.
Do not create any Notion database or page beyond the 3 databases and the rows listed here.
Do not create a Jira issue, a ticket, a task, a calendar event or a record in any other tool.
Do not write anything back into Salesforce after the rows in Part 3 are in.
Do not invent a feature, a person, an account, a changelog version or an error message.
Do not report anything as created when it was not.

Everything below is invented test data. No web search is needed for any of it. Larkfield Systems is a made up company, every account ID is invented, every feature name is invented, and every person named below is invented. No real client, real colleague, real customer or real credential goes anywhere in this run.

All dates use Asia/Kolkata. The master run works to a fixed scenario date of 2026-09-10 and a call window of 2026-09-10 through 2026-09-16 inclusive. Every date this setup writes into a field or a property is written exactly as given below in YYYY-MM-DD form, and every time is written in 24 hour form.

Salesforce takes date input in the org locale rather than in YYYY-MM-DD, and which locale that is depends on the org, so read it rather than assuming it. Setup, Company Information carries the Locale, and a rejected date field shows its own format hint beside it, so take the format off 1 of those before typing a single date. On a dd/mm/yyyy org 2026-09-12 gets typed as 12/09/2026, and on an mm/dd/yyyy org the same date gets typed as 09/12/2026, and typing the wrong 1 of those saves without complaint. Every date below is given in YYYY-MM-DD and gets converted on the way in rather than typed straight through. After saving any Salesforce record carrying a date, open the saved record and read the date back with the month named, because 12 September quietly landing as 9 December changes the answer the master run is meant to reach and nothing later in this setup would catch it.

THE 4 THINGS THAT CANNOT BE FAKED, READ THIS FIRST

Salesforce sets its own 18 character record Ids and its own created and modified stamps, and none of those can be chosen or backdated. That is fine, and the master run does not read any of them. It works off a plain text field called Account ID that this setup creates by hand, carrying values like ACC-401, so the account key the master run matches on is typed in rather than taken from Salesforce. Do not try to backdate anything in Salesforce and do not report that you did.

Salesforce adds __c to the API name of every custom object and custom field it creates. That is expected and does not matter. The master run reads field labels off the report and the record page, so the labels are what have to be exact. Leave whatever API name Salesforce lands on alone.

A Salesforce custom object cannot be reported on unless Allow Reports is ticked when the object is created. Tick it. If the object is already there without it, edit the object and tick it, otherwise Part 4 has nothing to build a report on.

The people named below do not exist in the Slack workspace, so a handle like priya.nair will not resolve to a real member. Write handles as plain text everywhere they appear in this setup and do not create Slack users for them. Nothing in this setup posts a message anyway.
