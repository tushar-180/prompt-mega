THE 3 THINGS THAT CANNOT BE FAKED, READ THIS FIRST

Jira sets the created and updated timestamps itself and they cannot be backdated. That is fine, and the master run does not read them. It works its date window off the Incident Start Timestamp line in the description, which is plain text typed in by hand, so that line is the one that has to be exact on every record. Do not try to backdate anything in Jira and do not report that you did.

GitHub Actions results cannot be hand written either. The master run settles whether tests passed on the most recent completed workflow run on the head commit of each pull request, so those runs have to be real. Push the workflow file, let the run finish, and check on the Actions tab that the run has actually completed with the result the brief asks for before you move on. A pull request with no completed run against it breaks the test this seed exists to set up. If a run will not complete, say so in the setup report with the exact error rather than describing a result that is not on the screen.

GitHub numbers pull requests itself, 1 upwards inside each repository, and that number cannot be chosen either. The Jira records in Part 2 quote pull request numbers that came off another tracker and none of them lines up with the real ones, which is deliberate, so type those quoted numbers into the descriptions exactly as written and let GitHub give the real pull requests whatever numbers they land on. The master run is supposed to find the pull request off the branch name rather than off that number, so this is a trap and not a mistake to tidy up. Write the real number each pull request got into the setup report.
